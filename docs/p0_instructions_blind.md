# P0 静的解析 指示書（盲検版 — 校正例は marnie/crustle のみ）
対象: L2 Discovery Pipeline の P0 フェーズ。1回の実行で1デッキを解析する。

## 0. あなたの役割と成果物
あなたはポケモンTCG（cabt シミュレータ環境）のデッキアナリストである。与えられた60枚のデッキを
**カードDBとルール知識のみ**から多面的に解析し、次の2つを出力する:
1. `docs/p0_<deck>_blind.md` — 人間可読の解析書
2. `docs/p0_<deck>_blind.json` — **検証可能な仮説リスト**（P1 テレメトリが自動照合する。最重要成果物）

**心構え**: あなたの仕事は「カードの役割ラベル付け」ではない。**「このデッキが勝つ手順の仕様」を書き、
それが崩れる箇所を予言する**ことである。汎用エンジン（L0）は「盤面を作り、最良アタッカーにエネを集中し、
撃てる時に撃つ」だけの床である。L0 が**このデッキ固有の理由で間違える箇所**を特定することが価値であり、
全ての主張は (a) カードテキスト・数値の引用、(b) 計測可能な指標、のどちらかに接地させること。

## 1. 入力と道具
- デッキ: `decks/<name>.csv`（カードID×60、1行1枚）
- カードDB: 以下で全文をダンプできる（攻撃コスト・ダメージ・テキスト・特性・HP・進化元）
```python
import sys; [sys.path.insert(0,p) for p in ('.','cg-lib')]
import library
from agents._engine import _CARDS, _ATTACKS
from collections import Counter
cnt = Counter(library.read_deck('<name>'))
# _CARDS[cid].name/.hp/.attacks/.skills/.evolvesFrom/.cardType/.energyType, _ATTACKS[aid].text/.damage/.energies
```
- **不確かな機構はシミュレータで実証する**（必須）。`tools/arena.py` の `play()` に自作の計測エージェント
  （選択肢を観察して記録する関数）を渡してセルフプレイでき、`cg.game.battle_start` で盤面を作って
  提示 option を確認するプローブもできる。テキスト解釈に自信の持てない効果（スケール式・エネの
  進化持ち上がり・特性の発動条件・技コストの型要求）は必ずプローブし、「実証済み/未実証」を明記する。
- **エネルギーコストは「数」でなく「型」まで見る**こと。技コストの型要求 vs このデッキのエネ供給型を
  必ず突き合わせる（型が永遠に揃わない「型死」ポケモンは実質アタッカーではない）。

## 2. 必須解析セクション（.md の章立て）

### §1 勝ち筋の仕様（win condition spec）
- 主勝ち筋を**手順として**記述: 「TnまでにXを場に、YにエネZ、以降毎ターンWを実行」
- 副勝ち筋・プランB（主砲が落ちた後/組めなかった時に何で勝つか）
- **実打点式**: スケール技（表示0ダメージ含む）は式で書く（例: ベンチ数×20、盤面エネ×30 等）。
  これは共有知覚 `_expected_dmg` の実装候補である。式の変数（手札・盤面エネ・ベンチ数…）が
  そのままこのデッキの「育てるべき資源」になる。

### §2 ルール相互作用の棚卸し
このデッキに関係する規則を列挙し、含意を書く。最低限チェックする項目:
- エネは進化で持ち上がる → 下位ラインへの**先貼り**が可能か/すべきか
- ダメカン**配置**か**ダメージ**か（配置は弱点・軽減・効果耐性を無視）
- 技コストの**型要求** vs デッキのエネ供給型（型死の検出）
- 1ターン1回制（サポート・手貼り・特性・逃げ）とこのデッキの理想シーケンスの衝突
- 自己ドロー/山掘りエンジンの有無 → **デッキアウト地平**（何ターンで山が尽きるか概算）
- ACE SPEC・スタジアム競合・特殊エネの供給型

### §3 サイド算術（prize arithmetic）
- 各アタッカーの HP vs 環境典型打点（~200前後）→ **「主砲は毎ターン取られる」前提か**
- 自分のアタッカーのサイド価値（1枚/ex2枚/mega3枚）と相手に与えるトレード
- 勝利までの必要KO数と、毎ターンKOを続けるための**チェイン要件**（何体目まで装填が要るか）

### §4 フェーズプラン（序盤・中盤・終盤）★
各フェーズを**計測可能に**定義する（曖昧な言葉は禁止。判定条件を状態変数で書く）:
| フェーズ | 遷移条件（状態変数） | このデッキの「計画通り」の定義 | 逸脱時のリカバリ |
- フェーズごとに「使うカード/使わないカード」を宣言（→ P1 のプレイ率と突き合わせる）

### §5 多面的評価軸（deck scorecard）★
基底8軸を**このデッキ固有の定義**で採点し（1-5）、**各軸に検証指標を紐付ける**。
デッキによって追加軸が必要なら**作る**（軸の発明こそ P0 の価値。このデッキの勝ち筋の変数から導け）。
基底軸:
1. **速度**: 初撃ターン/主勝ち筋 online ターンの理論値と分布
2. **火力曲線**: フェーズ別の期待打点（実打点式で）
3. **安定性**: 初手ブリック率（種無し・エンジン無し確率の概算）、引き込み冗長性
4. **継戦力**: 主砲KO後の再建コスト（何枚・何ターン）、回収ループの有無
5. **対応力**: 壁/スプレッド/エネ破壊/手札破壊それぞれへの回答の有無（カード名で）
6. **資源経済**: エネ供給レート vs 消費、山切れ地平、手札経済
7. **妨害耐性**: 相手の gust/hammer/手札リセットに崩される急所
8. **サイドレース構造**: トレード有利/不利の相手プロファイル
各軸の書式: `評価: n/5 / 根拠: <カード引用> / 検証指標: <P1テレメトリ名と期待値> / 欠けた時の修正候補`

### §6 カード別「使用宣言」（全カード必須）★
60枚全てについて: `カード名 ×n | 意図 | 発火条件（状態変数で） | 期待プレイ率/試合 | 腐る条件`
- **発火条件は汎用閾値でなくこのデッキの状態分布に較正する**こと。まず「このデッキの定常状態
  （手札枚数・盤面エネ・ベンチ構成の典型値）」を§1-2の機構から**推論**し、汎用エンジンの既定閾値
  （例: 手札≤5でドロー、60点以上で gust 等）がその分布で**発火するか**を1枚ずつ検査する。
  （校正例〔marnie〕: 逃げの既定「装填済みなら逃げない」は、エネ**数**は足りるが**型**が永遠に
  合わない壁ポケモンで誤作動し、本命へのスワップを永久阻害した。数でなく型・分布で検査せよ。）
- 期待プレイ率は P2 の死にカード監査の基準値になる。

### §7 敗因仮説と L2 規則候補
- 予想される敗因の分布（deckout/テンポ/レース/全滅…）と根拠
- 下の汎用パターン集から適用候補を列挙し優先順位をつける。無ければ**新パターンをテンプレとして**提案
  （症状→条件→修正の3点セット）。

**汎用パターン集（症状 → 定型修正）**:
| 症状 | 定型修正 |
|---|---|
| スケール技が過小評価される | 実打点式を共有知覚に昇格（gust/昇格/エネ配分が参照） |
| キーカードのプレイ率~0 | 発火条件を手札枚数等の汎用閾値から**盤面/手札の所持状態ベース**に置換 |
| エネが意図しないポケモンへ | デッキ固有の給餌計画（先貼り・キャップ・順序）を明示 |
| 主砲KO後に殴れない | 2体目の予備装填（チェイン、上限つき） |
| 山切れ負け | 山戻しカードの条件発火（deck≤N かつ 資源≥M） |
| キーカードがトラッシュで勝ち筋喪失 | 回収カードの所持ベース発火（再建ループ） |
| 攻撃せず抱え込み/遅延 | 攻撃優先の均衡則（消極性は本環境で一貫して有害） |
| gust が価値を逃す | サイド期待値・実打点ベースの対象選択 |
| 妨害カードの浪費/腐り | 相手盤面条件（撃つ寸前・特殊エネ有等）に限定 |
| 無差別ベンチ展開 | ベンチ許可リスト＋上限 |
| 型死ポケモンを装填扱い | 型対応の装填判定（数でなく型で「壁」と「装填中」を区別） |

## 3. JSON 仮説スキーマ（P1 が自動照合する）
```json
{
 "deck": "<name>",
 "expected_dmg": [{"pokemon": <cid>, "attack": "<name>", "formula": "<式>", "verified": true}],
 "phases": {"early": {"until": "<状態変数条件>", "on_plan": "<計測可能な定義>"}, "mid": {}, "late": {}},
 "hypotheses": [
   {"id": "H1", "claim": "<主張>", "metric": "<テレメトリ名>", "expect": "<比較式>",
    "violation_symptom": "<症状名>", "pattern": "<適用パターン>"}
 ],
 "card_intents": {"<cid>": {"name": "...", "trigger": "<状態条件>", "expected_play_rate": 0.5}},
 "axes": {"speed": 3, "power_curve": 4}
}
```
利用可能なテレメトリ名（P1 実装予定）: `play_rate[cid]`, `energy_attach_share[cid,...]`,
`post_ko_attack_rate`, `loss_share[deckout|prize|board]`, `hand_size_dist`, `bench_size_dist`,
`first_attack_turn`, `nonattacking_turn_rate`, `retreat_count`, `gust_targets`, `trigger_fire[rule]`。
- **hypotheses が本体**。「良い仮説」= 破られたときに適用すべきパターンが決まっている仮説。
  最低8本、フェーズ・軸・カード意図から満遍なく出すこと。

## 4. 品質基準（校正スイート）
⚠ **以下の事例に解析を引っ張られてはならない**（anchoring 禁止）。校正例は「見つけるべき種類の深さ」を
示すのであって「見つけるべき内容」ではない。軸・仮説は必ず**対象デッキの勝ち筋**から導出すること。

**(a) marnie_grimmsnarl（spread/wall 型）で過去に見つかった深さの実例**:
- 型死の検出（エネ数は足りるが型が永遠に合わない壁 → 装填判定の誤作動でスワップ永久阻害）
- 単一目的スワップ（逃げは「ベンチの本命が装填済みの時」のみ。他の逃げは全て損）
- 壁の昇格序列と給餌順序、加速の分配キャップ（gust 全損保険）

**(b) crustle_stall（陰性対照）**: 汎用 L1 で既に十分＝**「L2 不要」が正しい結論になるデッキが存在する**。
仮説が全て支持される見込みなら「L2 作成見送り」を推奨せよ。無理に症状を発明してはならない。

## 5. アンチパターン（不合格条件）
- 役割ラベルだけで発火条件が無い
- 計測不能な主張（「柔軟に立ち回る」「臨機応変に」）
- Web 記事の受け売りで我々の60枚に無いカードを前提にする
- スケール技・特性の解釈をプローブせず断定（verified フラグの偽装）
- 汎用閾値をこのデッキの状態分布を確認せず流用する
