# P0 静的解析 指示書 v2（zero-shot 版）
対象: L2 Discovery Pipeline（`docs/l2_pipeline.md`）の P0 フェーズ。1回の実行で1デッキを解析する。
本書は**意図的にデッキ固有の実例を含まない**（実例への anchoring を防ぐため）。品質の合否判定は
チェッカー側が外部基準で行う。あなたは対象デッキの勝ち筋**そのもの**から全てを導出すること。

## 0. あなたの役割と成果物
あなたはポケモンTCG（cabt シミュレータ環境）のデッキアナリストである。与えられた60枚を
**カードDBとルール知識のみ**から多面的に解析し、次の3つを出力する:
1. `docs/p0_<deck>.md` — 人間可読の解析書
2. `docs/p0_<deck>.json` — **検証可能な仮説リスト**（P1 テレメトリが自動照合する。最重要成果物）
3. JSON 内の `disposition_ledger` — 全仮説の空欄台帳。**P3 実装者は全仮説を
   「実装/延期(理由)/棄却(理由)」で必ず記入する契約**であり、severity=catastrophic の
   未実装は P4 を通過できない。

**心構え**: あなたの仕事は「カードの役割ラベル付け」ではない。**「このデッキが勝つ手順の仕様」を
書き、それが崩れる箇所を予言する**ことである。汎用エンジン（L0）は「盤面を作り、最良アタッカーに
エネを集中し、撃てる時に撃つ」だけの床である。L0 が**このデッキ固有の理由で間違える箇所**の特定が
価値であり、全ての主張は (a) カードテキスト・数値の引用、(b) 計測可能な指標、のいずれかに接地させる。

## 1. 入力と道具
- デッキ: `decks/<name>.csv`（カードID×60、1行1枚）
- カードDB:
```python
import sys; [sys.path.insert(0,p) for p in ('.','cg-lib')]
import library
from agents._engine import _CARDS, _ATTACKS
from collections import Counter
cnt = Counter(library.read_deck('<name>'))
# _CARDS[cid].name/.hp/.attacks/.skills/.evolvesFrom/.cardType/.energyType, _ATTACKS[aid].text/.damage/.energies
```
- **不確かな機構はシミュレータで実証する**（必須）。`tools/arena.py` の `play()` に計測エージェントを
  渡したセルフプレイ、`cg.game.battle_start` で盤面を作り提示 option を確認するプローブが使える。
  テキスト解釈に自信の持てない効果（スケール式・エネの進化持ち上がり・特性の発動条件と副作用・
  技コストの型要求・対象制限）は必ずプローブし、全ての機構的主張に `verified: true/false` を付す。
- **エネルギーコストは「数」でなく「型」まで見る**。技コストの型要求 vs このデッキのエネ供給型を
  全アタッカーで突き合わせる（型が永遠に揃わないポケモンは実質アタッカーではない）。

## 2. 必須解析セクション（.md の章立て）

### §1 勝ち筋の仕様（win condition spec）
- 主勝ち筋を**手順として**記述: 「TnまでにXを場に、YにエネZ、以降毎ターンWを実行」。
- 副勝ち筋・プランB（主砲が落ちた/組めなかった時に何で勝つか）。
- **実打点式**: スケール技（表示0ダメージ含む）は式で書く（damage = f(状態変数)）。
  式の変数がそのままこのデッキの「育てるべき資源」になる。式は共有知覚 `_expected_dmg` の実装候補。
- **複数ドクトリンの併記**: 実行可能なゲームプランが複数あり得る場合（例: 進化を場で行うか
  ベンチで組んで入れ替えるか、等の一般論としての分岐）は**決め打ちせず両方を仕様として書き**、
  JSON の `doctrines` に判別実験（discriminating metric での A/B）まで指定する。

### §2 ルール相互作用の棚卸し
このデッキに関係する規則を列挙し、含意を書く。最低限:
- エネは進化で持ち上がる → 下位ラインへの先貼りが可能か/すべきか
- ダメカン**配置**か**ダメージ**か（配置は弱点・軽減・効果耐性を無視）
- 技コストの型要求 vs デッキのエネ供給型（型死の検出）
- 1ターン1回制（サポート・手貼り・特性・逃げ）と理想シーケンスの衝突
- 自己ドロー/山掘りエンジンの有無 → **デッキアウト地平**（何ターンで山が尽きるか概算）
- ACE SPEC・スタジアム競合・特殊エネの供給型と支払い可能性

### §2b 自己害の棚卸し ★必須・severity 判定つき
60枚全てを対象に、**自分を害しうる効果**を走査し、該当カードごとに
「**発火してよい盤面条件**」を状態変数で宣言する。該当があれば必ず severity=catastrophic の
仮説を立てる（汎用エンジンは特性・トレーナーを無条件に使う既定を持つため、ここが最大の事故源）:
- 自身/自軍のポケモンを場から除去する特性・技（山・手札に戻す等）→ 最後の1体で使えば即敗北
- 手札を山に戻す/捨てるカード → 勝ち筋の中核を抱えた手で撃つと自壊
- 自傷ダメージ・自軍へのダメカン配置 → 蓄積の出口（移送・回復）があるか
- 自己ミル → デッキアウト地平と連動
- 強制入替・ベンチ限定効果 → 意図しない盤面露出

### §3 サイド算術（prize arithmetic）
- 各アタッカーの HP vs 環境典型打点（~200前後）→ 「主砲は毎ターン取られる」前提か
- 自アタッカーのサイド価値（1/ex2/mega3）とトレード構造
- 勝利までの必要KO数と、毎ターンKOを続けるための**チェイン要件**（何体目まで装填が要るか）

### §4 フェーズプラン（序盤・中盤・終盤）★
各フェーズを**計測可能に**定義（曖昧語禁止。判定条件は状態変数で）:
| フェーズ | 遷移条件（状態変数） | 「計画通り」の定義 | 逸脱時のリカバリ |
- フェーズごとに「使うカード/使わないカード」を宣言（→ P1 のプレイ率と突き合わせる）。

### §5 多面的評価軸（deck scorecard）＋ 対立軸 ★
基底8軸を**このデッキ固有の定義**で採点（1-5）し、各軸に検証指標を紐付ける。
必要なら**軸を発明**する（勝ち筋の式の変数から導け）。基底軸:
1. 速度（初撃/勝ち筋 online ターン） 2. 火力曲線（フェーズ別期待打点） 3. 安定性（ブリック率・冗長性）
4. 継戦力（再建コスト・回収ループ） 5. 対応力（壁/スプレッド/エネ破壊/手札破壊への回答）
6. 資源経済（エネ供給 vs 消費・山切れ地平・手札経済） 7. 妨害耐性（gust/hammer/手札リセットの急所）
8. サイドレース構造（トレード有利不利）
- **対立軸（tensions）を必須宣言**: 一方を最適化すると他方が悪化する軸ペアを列挙し、
  「意図するバランス点」を状態変数で書く（例の型: 「資源Xを消費する行動は条件Cの間のみ」）。
  デッキのエンジンが自分の敗因を兼ねる構造（掘るほど強く、掘るほど山が尽きる等）は必ずここに現れる。
  P3 への含意: tension に属する指標を修正する際は**対になる指標を同時監視**しないと whack-a-mole になる。

### §6 カード別「使用宣言」（全60枚必須）★
`カード名 ×n | 意図 | 発火条件（状態変数で） | 期待プレイ率/試合 | 腐る条件`
- **発火条件はこのデッキの状態分布に較正する**: まず「定常状態（手札枚数・盤面エネ・ベンチ構成の
  典型値）」を§1-2の機構から推論し、汎用エンジンの既定閾値がその分布で発火するかを1枚ずつ検査。
- **数値条件は調整可能パラメータとして書く**: `fire_if: X >= A (A∈{...候補範囲})` の形にし、
  併せて「**締めすぎると何の燃料を止めるか**」を1行で必ず書く（条件値は仮説であり P4 が較正する）。

**L0 既定の監査リスト**（汎用エンジンの実装事実。各項目がこのデッキで誤作動しないか1つずつ検査）:
- 特性は提示されれば**無条件に使う**（§2b の自己害と直結）
- エネ手貼りは「表示ダメージ最大のアタッカー」へ（スケール技の表示0は過小評価される）
- ドローサポートは手札≤5前後でのみ発火（手札を抱えるデッキでは死ぬ）
- サーチ/ボール系アイテムは**無条件に毎ターン使う**（山が薄くても掘り続ける）
- 進化は「進化後の表示ダメージ最大」を優先（勝ち筋のラインが後回しになり得る）
- 逃げは「装填済み（エネ数ベース）なら逃がさない」（型死の壁で誤作動する）
- gust は自 active の表示打点が60以上のときのみ（実打点式を知らない）
- KO後の昇格は「表示打点最大」（未装填の主砲を晒し得る）

### §7 敗因仮説と L2 規則候補
- 予想される敗因の分布（deckout/テンポ/レース/盤面全滅…）と根拠。
- 下の汎用パターン集から適用候補を列挙し優先順位をつける。無ければ**新パターンをテンプレとして**
  提案（症状→条件→修正の3点セット）。

**汎用パターン集（症状 → 定型修正）**:
| 症状 | 定型修正 |
|---|---|
| スケール技が過小評価される | 実打点式を共有知覚に昇格（gust/昇格/エネ配分/リーサル判定が参照） |
| キーカードのプレイ率~0 | 発火条件を汎用閾値から**盤面/手札の所持状態ベース**に置換 |
| エネが意図しないポケモンへ | デッキ固有の給餌計画（先貼り・キャップ・順序）を明示 |
| 主砲KO後に殴れない | 2体目の予備装填（チェイン、上限つき） |
| 山切れ負け | 山戻しの条件発火＋**山薄時の掘り停止**（掘り自体を止める側も要る） |
| キーカードがトラッシュ/山で勝ち筋喪失 | 回収カードの所持ベース発火（再建ループ） |
| 攻撃せず抱え込み/遅延 | 攻撃優先の均衡則（消極性は本環境で一貫して有害） |
| gust が価値を逃す | サイド期待値・実打点ベースの対象選択 |
| 妨害カードの浪費/腐り | 相手盤面条件（撃つ寸前・対象の存在等）に限定 |
| 無差別ベンチ展開 | ベンチ許可リスト＋上限 |
| 型死ポケモンを装填扱い | 型対応の装填判定（数でなく型で「壁」と「装填中」を区別） |
| 自己害効果の無条件発火 | 盤面状態ゲート（§2b の宣言条件を実装） |

## 3. JSON 仮説スキーマ（P1 が自動照合する）
```json
{
 "deck": "<name>",
 "expected_dmg": [{"pokemon": <cid>, "attack": "<name>", "formula": "<式>", "verified": true}],
 "phases": {"early": {"until": "<状態変数条件>", "on_plan": "<計測可能な定義>"}, "mid": {}, "late": {}},
 "doctrines": [{"name": "<プラン名>", "plan": "<手順>", "discriminating_metric": "<判別指標/A-B>"}],
 "tensions": [{"axes": ["<軸A>", "<軸B>"], "balance": "<状態変数で書いたバランス点>"}],
 "hypotheses": [
   {"id": "H1", "severity": "catastrophic|major|minor",
    "claim": "<主張>", "metric": "<テレメトリ名>",
    "direction": "<必ず成立すべき向き>",
    "threshold": {"value": "<暫定値>", "provisional": true, "params": {"<記号>": ["<候補範囲>"]}},
    "risk_of_overtightening": "<締めすぎると何の燃料を止めるか>",
    "scenario": "<catastrophic のみ必須: 危険が発火する盤面の構成手順（P4 regression 用）>",
    "violation_symptom": "<症状名>", "pattern": "<適用パターン>"}
 ],
 "card_intents": {"<cid>": {"name": "...", "trigger": "<状態条件>", "expected_play_rate": 0.5}},
 "axes": {"speed": 3, "power_curve": 4},
 "disposition_ledger": {"H1": null}
}
```
利用可能なテレメトリ名（P1 実装）: `play_rate[cid]`, `energy_attach_share[cid,...]`,
`post_ko_attack_rate`, `loss_share[deckout|prize|board]`, `hand_size_dist`, `bench_size_dist`,
`first_attack_turn`, `nonattacking_turn_rate`, `retreat_count`, `gust_targets`, `trigger_fire[rule]`。
- **hypotheses が本体**。「良い仮説」= 破られたときに適用すべきパターンが決まっている仮説。
  最低8本。§2b に該当カードがあるなら catastrophic を最低1本含めること。
- **threshold は事前分布**であり合否線ではない: P2 は direction 違反＝症状、threshold 違反＝
  「較正 or 修正」の2択として扱う。可能なら L0/既存実装の同指標を先に測って基準化せよ。

## 4. 品質基準（zero-shot・定量）
出力は以下を全て満たすこと（チェッカーが外部基準で照合する）:
- 実打点式: 表示と実効が乖離する技**全て**に式＋verified フラグ
- 型検査: 全アタッカーで「コストの型 vs 供給型」の突き合わせ結果を明記
- §2b: 60枚走査の結果を明記（該当なしなら「なし」と書く。該当ありなら catastrophic 仮説＋scenario）
- §6: 60枚全てに発火条件つき使用宣言。汎用閾値の流用は状態分布の検査つきでのみ可
- tensions: 最低1組（真に無い場合は「なし」と根拠を書く）
- 仮説≥8本（direction/threshold 分離、params と risk_of_overtightening つき）
- **「L2 不要（L1で十分）」は正当な結論である**。仮説が全て支持される見込みなら
  「L2 作成見送り」を推奨せよ。症状の発明は不合格事由である。

## 5. アンチパターン（不合格条件）
- 役割ラベルだけで発火条件が無い
- 計測不能な主張（「柔軟に」「臨機応変に」）
- Web 記事の受け売りで実60枚に無いカードを前提にする
- 機構をプローブせず断定（verified の偽装）
- 汎用閾値を状態分布の検査なしに流用
- 固定の数値ゲートを較正余地なしに宣言（params 無し・締めすぎリスク未記載）
- 単一ドクトリンへの決め打ち（代替プランの検討痕跡が無い）

## v2 REQUIRED ADDITIONS (pipeline v2)
Besides the hypothesis/intent sections above, the JSON MUST include:
- `lines`: 1-3 named playbooks, each with `setup` (board targets by turn),
  `loop` (the repeatable turn), `finisher`, and `invariants` — measurable board
  properties in telemetry vocabulary: {"type":"stadium_in_play","cid":..,"by_turn":..},
  {"type":"armed_bodies","cid":..,"energy":<EnergyType int>,"min_energy":..,"count":..,"by_turn":..},
  {"type":"attack_rate_after","turn":..,"min":..}.
- `combo_edges` per line: cross-card dependency edges, each flagged
  `individually_negative` (true ⇒ this edge may only be A/B-tested as part of
  the whole line bundle, never alone).
- Any mechanism claim that an L2 rule will rely on (damage formula, lock/effect
  semantics, sub-select structure) must cite FORCED-CHOICE probe evidence, not
  observations of the default pilot piloting itself.
